## 1. 需求与优先级

### 1.1 原始需求

在启动 BetterGI 前把原神客户端更新好，避免 BGI 因旧客户端而整轮失败。三个硬条件：

1. **增量优先**：更新必须是增量更新（官方 ldiff 差分包），MAS 自己完成，不依赖开官方启动器。
2. **全量必须指出**：若本次只能全量（全新安装 / 逐文件全量比对 / 预下载），必须明确告知用户，不得静默执行。
3. **不加剧配置**：不为这个功能让用户额外配置启动器路径等内容。

### 1.2 手段优先级

| 优先级 | 手段 | 本期 |
| --- | --- | --- |
| 首选 | **静默增量安装**（MAS 自己拉差分、下 patch chunk、hpatchz 落盘） | 做 |
| 次选 | OCR 驱动官方启动器更新（NTE 式） | 不做，留作后续 |
| 再次 | 「直接启动游戏报版本错误 → 拉起启动器」兜底 | 不做：需用户额外配启动器路径，且 BGI 可原生拉起游戏 |
| 末选 | 全量更新 | 不做，且必须指出 |

> OCR 仅适用于「游戏无法原生拉起、只能经启动器拉起」的场景（如 OK-NTE）。BetterGI 能原生拉起游戏，因此走静默安装而非界面识别。

## 5. 接口契约（已逐条核验）

### 5.1 区服常量

| | info base | downloader base | launcher_id | plat_app |
| --- | --- | --- | --- | --- |
| 官服 | `https://hyp-api.mihoyo.com/hyp/hyp-connect/api` | `https://api-takumi.mihoyo.com` | `jGHBHlcOq1` | `ddxf5qt290cg` |
| 国际服 | `https://sg-hyp-api.hoyoverse.com/hyp/hyp-connect/api` | `https://sg-public-api.hoyoverse.com` | `VYTpXlbWo8` | `ddxf6vlr1reo` |

### 5.2 端点

| 用途 | 路径 | 方法 | 参数 |
| --- | --- | --- | --- |
| 游戏列表 | `{info}/getGames` | GET | `launcher_id`、`language` |
| 分支信息 | `{info}/getGameBranches` | GET | `game_ids[]`、`launcher_id` |
| 主清单 | `{downloader}/downloader/sophon_chunk/api/getBuild` | **GET** | `branch`、`package_id`、`password`、`tag` |
| 差分清单 | `{downloader}/downloader/sophon_chunk/api/getPatchBuild` | **POST**（发 GET 会被判 405） | 查询串与 `getBuild` 同形 |

**两个必须遵守的坑：**

1. `tag` 必须用 API 返回的**原始 3 段版本串**（如 `7.0.0`）。补成 4 段（`7.0.0.0`）会被服务端判 `-202 not found`。
2. **基线版本不在 URL 上**。`getPatchBuild` 的响应里每份清单带 `diff_tagged_info`，以基线版本为键，由调用方按本机已装版本去挑；挑不到即视为「无可用差分」。

### 5.3 补丁三类判定 + 删除

以**差分清单点名的文件**为准，逐个对到目标版本主清单：

| 情形 | 处理 |
| --- | --- |
| 差分清单未点名 | **不动**（本机已有且内容一致） |
| 点名，chunk 无 `original_file_name` | **CopyOver** — patch chunk 本身就是新内容，直接落盘 |
| 点名，chunk 有 `original_file_name` | **Patch** — 用 hpatchz 把补丁打到旧文件上 |
| `unused_assets[]` 且目标清单不再使用 | **Remove** — 删除旧文件 |

> **增量/全量的分界就在这里。** 若把「差分清单未点名」的文件也当作整文件重下，一次约 10 GB 的增量会变成上百 GB 的全量下载。这是本实现与 `HoyoSophonDL`（只按 MD5 挑变更文件后整文件重下）的根本差别。

### 5.4 hpatchz

调用形式：`hpatchz -f <oldFile> <diffFile> <outNewFile>`。
获取：复用 `app/utils/hpatchz.py` 的 `ensure_hpatchz()`（sha256 固定校验、按需下载到 `data/cache/hpatchz/`、原子落位），不重写。

### 5.5 protobuf

使用上游社区维护的 `.proto` 定义（`SophonManifestProto.proto` / `SophonPatchProto.proto`）配合 protoc 生成物，**不手写 wire 解码器**。理由：`length-delimited` 字段把 bytes/string/嵌套消息编码得完全同构，手写解码必须按已知 schema 显式声明嵌套关系，否则退化为启发式判断而误判。

**约束**：生成代码带 runtime 版本校验（`ValidateProtobufRuntimeVersion(..., 6, 31, 1, ...)`），因此 `protobuf` 必须是**受约束依赖**（pin 具体版本），不能浮动。`.proto` 源文件一并入库，并说明再生成方式。

## 8. 行为策略

| 情形 | 行为 | 依据 |
| --- | --- | --- |
| 开关关闭 | 完全不介入，不写日志 | 避免无关任务刷日志 |
| 查询接口不可用 / 无法判定 | **放行**启动流程 | 旧客户端通常仍能登录，不该因查不到版本拦住用户（OKWW 既有语义） |
| 确认需更新但更新失败 | **阻断**本次任务，给出失败原因 | 拿旧客户端撞登录只会白跑一轮 |
| 已是新版 | 放行，仅记 `app.log` | 不占用任务日志 |
| 差分可得 | **自动完成增量更新** | 需求第 1 条 |
| 仅可全量（全新安装 / 逐文件全量比对） | **停手 + 明确指出**种类与体积，建议用官方启动器 | 需求第 2 条 |
| 官方已开放预下载 | 仅记一行「暂不接管预下载」，**不阻断** | OKWW 既有语义 |
| 渠道为 B服 | **硬拒绝**并说明原因 | B服是独立渠道、版本节奏不同，用官服清单更新会写坏客户端 |
| 渠道无法识别 | 放行，留 `app.log` | 不改变任务命运 |

## 9. 可靠性设计

| 关注点 | 做法 |
| --- | --- |
| 不把游戏搞坏 | 暂存目录落盘 → 逐 chunk 校验 `ChunkDecompressedHashMd5` → 校验整文件 MD5 → 同卷原子替换 |
| 路径穿越 | 清单里的路径必须过校验（拒绝绝对路径、盘符、`..`、指向目录自身）。OKWW 的 `safe_relative_path` 是现成先例，其注释明确记载「历史上 okww 因缺此校验清空过项目源码」 |
| 并发 | 按**游戏目录**加互斥锁：多用户共用同一客户端时不可并行更新 |
| 中止 | 协作式：时限/取消到点在 chunk 与文件边界轮询收工；**不回滚已落盘的合法文件，也不写版本号** → 重开即续传 |
| 半更新状态安全性 | 版本号不写回，客户端仍认为自己是旧版，失败模式安全（不会带病启动） |
| 游戏在跑 | 更新前用 `find_running_game_exe` 检测，在跑则中止并提示 |
| 权限 | 目录不可写时提前失败，给出明确原因 |
| 磁盘门禁 | 按「暂存 + 在飞峰值 + 缓冲」估算，不足则提前停手 |
| 协议变动 | 任一步不符预期即 fail-fast，提示改用官方启动器，绝不猜着往下写 |

## 11. 验证方案

1. **只读探测（先做）**：`plan()` 联网算清单但**不落盘**，输出安装态、计划种类（`patch` / `install` / `update` / `preload` / `noop`）、文件数、待下字节、待删数、磁盘估算，并给出**「增量 or 全量」的判定依据**（差分清单点名数、`CopyOver` 与 `Patch` 各多少）。
2. **与官方口径对齐**：在有旧客户端的机器上只算不做，把预测下载量与官方启动器显示的更新体积对比。
3. **端到端**：`CopyOver` 分片落盘后校验 MD5；`Patch` 路径实打一次并比对目标文件 MD5。
4. **边界用例**：混装目录、无 `config.ini`、磁盘不足、游戏在跑、渠道为 B服、时限到点中断、接口不可用，各自行为需可复现。
5. **门槛命令**：`ruff check` / `ruff format --check`；前端 `yarn lint` / `yarn typecheck`。
6. **测试不提交**：按仓库规则，本功能的测试属一次性验证产物，本地跑通并把命令与结论写进 PR 正文，不入库。

## 12. 风险与未决项

| 风险 | 说明 |
| --- | --- |
| 无真实旧客户端则端到端不全 | 「hpatchz 打完补丁后目标 MD5 命中」需在装有旧客户端的机器上确认；否则只能按分段长度与 `CopyOver` 间接验证（与 PR #1002 作者遇到的是同一个瓶颈） |
| hpatchz 对 Sophon ldiff 的等价性 | 最大未知项，需实机确认 |
| `config.ini` 回写范围 | 除版本号外是否需写音频语言清单，需实测确认官方启动器行为。漏写可能致语音资源异常，多写可能污染 |
| 协议非官方 | 米哈游改动即失效，故必须 fail-fast、绝不半途写入不可控状态 |
| 任务超时 | 一次增量实测约 10 GB，需确认调度层超时不会中途掐断，否则需另设时限兜底 |
| `protobuf` 版本约束 | 生成物的 runtime 校验要求 pin 版本，需同步 `pyproject.toml` / `requirements.txt` / `uv.lock` |
